# wpsscanner 0.1.0 → 0.2.0 重构对比

本文记录 `wpsscanner` 从 0.1.0 到 0.2.0 的主要变化、设计取舍和迁移方式。
本次重构保留了原项目最重要的设计：**按路径作用域识别伪 404 页面**，重点改善检测准确率、请求效率、工程结构和命令行能力。

## 1. 总览

| 方面 | 0.1.0 | 0.2.0 |
| --- | --- | --- |
| 项目定位 | 简单路径扫描 Demo | 可测试、可配置的轻量路径扫描器 |
| 伪 404 基线 | 每个作用域固定请求 5 次 | 根目录基线 + 目录探测 + 按需建立目录基线 |
| 指纹内容 | 正文前 1 KiB | 规范化正文、长度、标题、状态码、重定向目标 |
| 动态内容处理 | 不处理 | 路径、UUID、时间、长数字、长十六进制等归一化 |
| 基线稳定性 | 只要成功样本超过 2 个就启用 | 样本相互比较，一致性达标后才启用 |
| 有效状态码 | 仅 200 | 默认保留 2xx、常见 3xx、401、403、405，可配置 |
| 重定向 | 强制跟随 | 默认不跟随，可通过参数开启，并记录目标地址 |
| HTTP 连接 | 每次调用 `requests.get()` | 每个工作线程复用 `requests.Session` |
| TLS | HTTPS 固定 `verify=False` | 默认验证证书，`--insecure` 显式关闭 |
| 响应读取 | 完整读取响应 | 最多读取 256 KiB，降低异常大响应的内存消耗 |
| 错误处理 | 所有异常静默转换为 `(None, None)` | 保留异常类型，调试模式可输出具体原因 |
| 停止逻辑 | 累计 20 个连接失败或 5xx | 连续网络错误阈值，可通过 `--max-errors` 配置 |
| 任务提交 | 一次提交整个字典 | 最多维持 `线程数 × 2` 个待处理任务 |
| 输出 | URL 文本 | 文本或 JSONL，包含状态、长度、标题、重定向和耗时 |
| 打包 | `setup.py` + 分散依赖 | 统一使用 `pyproject.toml` |
| 测试 | 无 | 10 个单元及本机 HTTP 集成测试 |
| CI | 无 | GitHub Actions 测试矩阵 |

## 2. 项目结构变化

### 0.1.0

```text
wps.py
src/wpsscanner/
├── __init__.py
├── cli.py
├── path_detector.py
└── utils.py
```

`cli.py` 从 `path_detector.py` 通配符导入，而 `path_detector.py` 又从 `utils.py` 通配符导入。CLI 使用的 `argparse`、`os`、`Event` 和 `tqdm` 等名称实际上依赖间接导入，模块之间耦合较强。

### 0.2.0

```text
wps.py
src/wpsscanner/
├── __init__.py
├── cli.py             # 参数、扫描编排、结果输出
├── http_client.py     # Session、限速、超时、代理、请求读取
├── models.py          # 响应、指纹、基线、结果数据模型
├── path_detector.py   # 基线管理、路径检测、并发调度
└── utils.py           # URL、正文和参数解析工具

tests/
├── test_detector.py
└── test_utils.py
```

新版本使用显式导入，并按职责拆分 HTTP、数据模型、算法和 CLI，降低了模块间隐式依赖。

## 3. 伪 404 检测算法

### 3.1 旧版算法

旧版会为字典中的每个一级目录作用域创建状态：

```text
/              → 根目录基线
admin/         → /admin/ 基线
api/           → /api/ 基线
```

每个作用域第一次扫描时：

1. 生成 5 个长度为 12 的随机路径。
2. 请求这些随机路径。
3. 只保留状态码为 200 且正文非空的响应。
4. 成功样本超过 2 个时启用基线。
5. 只截取正文前 1 KiB。
6. 使用 `SequenceMatcher` 和固定阈值 0.7 比较候选响应。

旧版的优点是不同目录可以拥有不同错误页面；主要问题是每个目录都固定增加 5 个请求，而且正文开头相似的正常页面容易被误过滤。

### 3.2 新版分层基线

0.2.0 使用根目录和目录级基线的分层策略：

```text
建立根目录基线
       │
       ├── 目录探测结果与根目录一致 → 继承根基线
       │
       └── 目录行为不同 → 补充样本，建立独立目录基线
```

具体流程：

1. 根目录默认请求 3 个随机不存在路径。
2. 每个一级目录先发送 1 个探测请求。
3. 如果目录探测结果与根基线相似，该目录直接继承根基线。
4. 如果不相似，再补充 2 个样本，建立目录专属基线。
5. 计算基线样本之间的平均相似度，选择最具代表性的样本。
6. 只有一致性达到 `--baseline-consistency` 时，基线才有资格过滤候选结果。
7. 单个成功样本不会被视为稳定基线。

在大量目录共用同一错误模板时，每个目录的额外基线请求从 5 次降至 1 次；只有行为不同的目录才使用完整的 3 个样本。

### 3.3 正文归一化

旧版直接比较原始正文前 1 KiB。新版先提取最多 16 KiB 的可见文本，并处理常见动态数据：

- 删除 `script` 和 `style` 内容；
- 删除 HTML 标签；
- 解码 HTML 实体；
- 转换为小写并合并连续空白；
- 替换扫描器随机探测路径；
- 替换响应中反射的当前请求路径；
- 替换 UUID；
- 替换 ISO 风格时间；
- 替换长数字和长十六进制值。

例如以下两个响应会形成相同的稳定文本：

```text
Unknown /.wpsscanner-404-aaaaaaaaaaaaaaaa at 2026-01-01 10:20:30
Unknown /missing-page at 2026-02-02 11:30:40
```

归一化后近似为：

```text
unknown <request-path> at <time>
```

这可以处理错误页面回显请求地址、请求 ID 或生成时间的情况。

### 3.4 复合指纹

旧版只有正文相似度。新版会综合以下信号：

| 信号 | 默认权重 | 作用 |
| --- | ---: | --- |
| 规范化正文 | 0.55 | 判断页面主要内容是否一致 |
| 响应长度 | 0.20 | 辅助识别模板和空响应 |
| 页面标题 | 0.10 | 识别统一错误页标题 |
| HTTP 状态码 | 0.10 | 区分正常响应和错误响应 |
| 重定向目标 | 0.05 | 识别统一跳转到登录页或首页的伪路径 |

仅对实际存在的信号重新归一化权重。因此，对于没有正文、但状态码和重定向目标相同的 302 响应，仍然可以形成稳定指纹。

候选结果达到 `--soft404-threshold` 才会被判定为伪 404。默认值为：

```text
基线一致性阈值：0.72
候选匹配阈值：0.82
```

## 4. HTTP 行为变化

### 4.1 状态码

旧版最终只输出 HTTP 200。新版默认保留：

```text
200-299,301,302,307,308,401,403,405
```

可通过以下方式调整：

```bash
wpsscanner -u https://example.com -w paths.txt \
  --status 200-204,301,302,401,403
```

404 和 410 会直接作为不存在页面处理。对于站点统一返回 200、302 或 403 的未知路径，则继续使用基线判断。

### 4.2 重定向

旧版固定跟随所有重定向，因此原始 301/302 容易变成最终 200。新版默认不跟随重定向，并记录 `Location` 目标：

```text
302  0  https://example.com/admin -> https://example.com/login
```

需要旧版行为时可以使用：

```bash
--follow-redirects
```

### 4.3 TLS

旧版对所有 HTTPS 请求关闭证书验证，并全局隐藏警告。新版默认验证 TLS 证书。需要扫描使用自签名证书的站点时显式使用：

```bash
--insecure
```

### 4.4 连接和响应资源

新版为每个工作线程复用一个 `requests.Session`，以使用连接池和 HTTP Keep-Alive。同时只读取每个响应的前 256 KiB，避免异常大响应占用过多内存。

## 5. 并发和停止机制

旧版会提前把整个字典提交到 `ThreadPoolExecutor`。大字典会创建大量 future，即使按下 Ctrl+C，大量任务也已经进入等待队列。

新版使用有界提交：

```text
最大待处理任务数 = 工作线程数 × 2
```

完成一个任务后才提交下一个任务。停止时会：

1. 设置共享 `Event`；
2. 停止继续提交；
3. 取消尚未执行的 future；
4. 等待正在执行的请求按配置的超时结束；
5. 关闭线程使用的 Session。

旧版名为 `num_502` 的计数器实际混合统计连接失败和所有 5xx。新版只将真实网络异常纳入连续错误计数，并允许配置：

```bash
--max-errors 20
```

## 6. 输入和输出

### 6.1 输入清理

新版读取字典和目标列表时会：

- 忽略空行；
- 忽略以 `#` 开头的注释；
- 保持原顺序去重；
- 验证目标是否为 HTTP/HTTPS URL；
- 对未提供协议的目标默认补充 `http://`；
- 拒绝空字典和空目标列表。

### 6.2 结构化结果

新版每个有效结果包含：

```text
url
path
scope
status
length
title
redirect_url
elapsed_ms
```

文本输出示例：

```text
403    1532    https://example.com/admin [Forbidden]
302    0       https://example.com/manage -> https://example.com/login
```

JSONL 输出：

```bash
wpsscanner -u https://example.com -w paths.txt --format jsonl -o results.jsonl
```

结果会在输出前按 URL 去重和排序，因此多线程执行顺序不会影响最终文件顺序。

## 8. 安装和打包

### 0.1.0

项目同时使用简单 `pyproject.toml`、`setup.py` 和逐项列举依赖的 `requirements.txt`。执行 `pip install .` 时，`setup.py` 没有自动声明运行依赖。

### 0.2.0

项目元数据和依赖统一到 `pyproject.toml`：

```toml
[project]
name = "wpsscanner"
version = "0.2.0"
dependencies = [
    "requests>=2.31,<3",
    "tqdm>=4.66,<5",
]
```

开发安装：

```bash
pip install -e .
```

安装测试和代码检查工具：

```bash
pip install -e '.[dev]'
```

`requirements.txt` 中的：

```text
-e .
```

是兼容 `pip install -r requirements.txt` 使用习惯的入口；真实依赖由 `pyproject.toml` 管理。

## 10. 兼容性变化

以下行为与旧版不同，升级时需要注意：

1. 默认线程数从 40 调整为 20，降低对目标和本机的瞬时压力。
2. 默认不跟随重定向；需要旧行为时添加 `--follow-redirects`。
3. 默认验证 TLS；需要旧行为时添加 `--insecure`。
4. 输出文件不再只包含 URL，而是包含状态码和响应信息。
5. 需要纯 URL 数据时，可对文本输出取第三列，或解析 JSONL 的 `url` 字段。
6. `PathDetector.run()` 的结果从两个普通列表改为 `ScanResult` 列表和递归目标列表组成的元组。
7. Python 最低版本从 3.8 调整为 3.9。

## 11. 仍然存在的限制

0.2.0 是小规模重构，并非完整扫描框架，目前仍有以下边界：

- 只支持 GET 路径扫描；
- 递归扫描仍限制为一层；
- 没有按目标单独配置认证信息；
- 没有断点恢复；
- 没有响应内容持久化；
- 正文相似度仍属于启发式算法，需要针对特殊站点调整阈值；
- JavaScript 单页应用的统一壳页面可能需要额外的语义检测策略；
- 没有自动学习登录失效或 WAF 拦截页面。

## 12. 总结

0.1.0 验证了“按目录建立伪 404 基线”的可行性；0.2.0 将这一思路升级为分层、可验证的检测流程：

```text
按目录识别
  + 根基线复用
  + 目录差异探测
  + 基线稳定性检查
  + 动态内容归一化
  + 多信号复合指纹
```

这次重构没有改变项目的核心方向，而是减少了基线请求、降低误报与漏报风险，并为后续继续优化检测算法建立了更清晰的代码边界和测试基础。
